# Trainy v0.2 Domain and Access Design

## Purpose and status

This document converts `requirements.md` into an implementation boundary for
the existing Hono, Better Auth, Drizzle, and PostgreSQL application. It does not
resolve the product and policy decisions listed under **Blockers**. The current
route and schema modules remain the source of truth until the migrations and
contracts below are implemented.

## Domain boundaries

- **Authentication** (`modules/auth`, `db/schema/auth.ts`) owns credentials,
  external provider accounts, sessions, email verification, password recovery,
  and secure account linking. Better Auth must hash and compare passwords.
- **Identity and access** (new module and schema) owns the provider-independent
  user identity, global account state, and the active-account gate. Organization
  roles remain tenant-scoped in `organization_membership`.
- **Registration** (`modules/onboarding`) owns role requests, evidence, review,
  rejection, revision, approval, and suspension initiation. A request never
  grants access; an approved active membership does.
- **Privacy** (new module and schema) owns versioned required-processing
  acknowledgements and separately versioned optional consent.
- **Internship request** (`modules/internship-requests`) owns student-authored
  request data, ordered decisions, resubmission, cancellation, and generated
  request-document metadata.
- **Placement and activity** (`modules/placements`, `attendance`, `progress`)
  own the active internship, assignments, schedule, attendance, and periodic
  logs. A program policy determines whether logs are daily or weekly.
- **Evaluation** (`modules/evaluations`) owns rounds, opening and closing dates,
  evaluator assignments, drafts, final submissions, and disclosure policy.
- **History, notification, and audit** (`modules/notifications`, new history
  projection, `db/schema/system.ts`) receive domain events. Consequential state
  changes and their audit event must commit atomically.

`shared` should export stable enums and request/response DTOs for these
boundaries. Hono's inferred client type may supplement, but must not replace,
explicit workflow and pagination contracts.

## State machines

### Account and registration

Current implementation:

```text
Better Auth session -> onboarding request
onboarding: pending -> approved | rejected | revision_requested
revision_requested -> pending
pending student -> approved immediately (current shortcut)
membership: active | suspended
```

Required implementation (students may take the verified automatic branch):

```text
account: pending_email -> verified role request
                              |             |
                    student auto-approval   +-> pending_approval -> active
                              |                         |             |
                              v                         v             v
                            active                   rejected      suspended

registration request:
draft/verified input -> pending -> approved | rejected | changes_required
                                      ^                        |
                                      +---- corrected/resubmitted+
```

Rules:

- Email/password applicants cannot enter automatic student approval or
  `pending_approval` before email verification. LINE applicants without a
  verified contact email remain `pending_email`.
- A student request may transition directly to `active` only after server-side
  student evidence and active-university checks succeed. All other roles use
  the authorized manual approval path.
- Approval atomically creates or activates the authorized membership, changes
  the account to `active`, and records actor, timestamp, reason, and audit event.
- Rejection requires a reason. Suspension revokes protected access without
  deleting identity, credentials, history, or prior decisions.
- Editing `requestedRole`, profile evidence, or any client field cannot create a
  membership or change account state.
- The existing automatic student approval is retained. It must create the same
  immutable transition audit evidence as a manual approval and must never trust
  a client-supplied role without server-side validation.

### Internship request

Current implementation:

```text
submitted -> advisor -> program_chair -> center -> approved
    |              each step may reject or request revision
    +-> cancelled
revision_requested -> submitted (same request and reset decisions)
```

Required product states and mapping:

| Required state     | Proposed persisted meaning                           |
| ------------------ | ---------------------------------------------------- |
| `draft`            | Student-owned, editable, no approval rows opened     |
| `submitted`        | Confirmed submission; approval workflow created once |
| `waiting_advisor`  | Advisor step is pending                              |
| `waiting_staff`    | Program-chair or center step is pending              |
| `changes_required` | Returned to student with reason; editable            |
| `approved`         | All required steps approved                          |
| `cancelled`        | Student cancellation recorded; terminal              |

`rejected` may remain as an internal terminal decision only if policy
distinguishes permanent rejection from correctable changes. Formal submission,
resubmission, approval, return, and cancellation require one transactional
history/audit event. A client idempotency key must make retries return the same
result rather than create a second request or decision.

### Activity log

Current `progress_report` states are:

```text
draft -> submitted -> approved
                   -> revision_requested -> draft/update -> submitted
```

The required public vocabulary is:

```text
draft -> submitted -> approved
                   -> changes_required -> draft/update -> submitted
```

Rename or map `revision_requested` to `changes_required` at the API boundary.
The selected program policy must determine daily versus weekly periods,
required fields, reviewer, due dates, and whether attendance contributes to
reported totals. Submitted and approved records retain immutable decision
history even when the editable content is revised.

### Evaluation

Current implementation supports `draft -> submitted` per placement and
evaluator type, but has no round schedule or disclosure policy.

Required implementation:

```text
scheduled (before opensAt) -> open -> draft -> submitted (immutable)
                                  \-> overdue/closed when closesAt passes
```

An evaluation assignment binds a round, placement, evaluator, evaluator type,
and visibility policy. Save is idempotent and allowed only while open. Final
submit is idempotent, records one audit event, and cannot be edited afterward.
Student result responses must be projected through the university disclosure
policy; raw scores and comments must not be returned by default.

## Deny-by-default permission matrix

All protected checks run on the server. `404` is preferred where revealing a
cross-tenant resource would leak its existence. Suspended memberships never
grant a permission.

| Capability                     | Pending/rejected/suspended | Student owner         | Assigned advisor | Authorized university staff | Assigned supervisor     | Company admin               | Platform staff   |
| ------------------------------ | -------------------------- | --------------------- | ---------------- | --------------------------- | ----------------------- | --------------------------- | ---------------- |
| Account status/remediation     | Own only                   | Own                   | Own              | Own                         | Own                     | Own                         | Own              |
| Submit registration request    | Own, when eligible         | N/A                   | N/A              | N/A                         | N/A                     | N/A                         | N/A              |
| Review registration            | Deny                       | Deny                  | Deny             | Configured scope only       | Deny                    | Configured scope            | System scope     |
| Read/update own profile        | Status-safe fields only    | Own                   | Own              | Own                         | Own                     | Own                         | Own              |
| Create/edit internship request | Deny                       | Own/editable          | Deny             | Deny                        | Deny                    | Deny                        | Deny             |
| Review internship request      | Deny                       | Deny                  | Assigned step    | Authorized step/scope       | Deny                    | Deny                        | Policy only      |
| List advisor student directory | Deny                       | Deny                  | Academic scope   | Academic scope              | Deny                    | Deny                        | Policy only      |

The matrix grants no capability merely because a user has a valid session. A
request must pass account state, active membership, role, tenant, assignment,
resource state, and disclosure checks applicable to that operation.

## Proposed API and system boundaries

### Authentication and account status

- Better Auth remains mounted at `/api/auth/*` for sign-up, sign-in, verified
  LINE OIDC, email verification, password reset, password change, and sessions.
- Add `/api/v1/account/status` and narrowly scoped remediation endpoints. They
  are available to authenticated non-active accounts.
- Add `requireActiveAccount` before every other `/api/v1/*` business route.
  Health remains public; registration, privacy acknowledgement, and account
  remediation receive explicit exceptions.
- Add authenticated link/unlink endpoints that require recent authentication
  or recovery proof. Reject unlinking the final authentication method.

### Registration and privacy

- Keep `/api/v1/onboarding`, but store immutable decision attempts separately
  from the mutable application snapshot.
- Add `/api/v1/privacy/current` and `/api/v1/privacy/acknowledgements`. Required
  acknowledgement gates protected profile completion; optional consent is a
  separate record and action.

### Portal read models

- Add `/api/v1/home/student` and `/api/v1/home/advisor` as server-composed,
  action-first read models. They return current action, responsible party,
  progress, milestones, and dated exceptions without exposing unauthorized
  detail.
- Add `/api/v1/advisor/students` with server-side `category`, `query`,
  `internshipState`, `academicTerm`, and cursor pagination. Return counts from
  the same authorized predicate as results.
- Add `/api/v1/advisor/students/:userId` as a permitted aggregate of timeline,
  request, placement activity, evaluations, and contact projection.
- Add `/api/v1/history` with category filters and cursor pagination. It reads
  immutable domain events and links documents to their originating event.

### Consequential writes

Formal request submission, cancellation, approval/return, placement terminal
transitions, and final evaluation submission accept an `Idempotency-Key` header.
The key is scoped to actor, operation, and target; request hash mismatch is a
conflict. The response and domain event commit with the state change. CORS must
explicitly allow this header.

## Migration and delivery sequence

1. **Freeze contracts.** Resolve the blockers below and add shared account,
   registration, request, log, evaluation, pagination, and error enums/DTOs.
2. **Additive identity migration.** Add provider-independent identity/account
   state, registration decisions, privacy acknowledgements, and idempotency
   records. Backfill existing users conservatively; do not infer approval from
   email or an OAuth profile.
3. **Authentication configuration.** Enable verified email/password and reset
   flows, retain LINE Authorization Code + PKCE, and add linking/unlinking
   controls. Test enumeration, callback replay, and provider-email collisions.
4. **Access gate migration.** Deploy account-status resolution and observe it
   before enforcing `requireActiveAccount`. Then deny protected access and
   expose only status/remediation routes to non-active accounts.
5. **Registration migration.** Preserve verified student auto-approval, move
   automatic and manual approvals plus suspensions to transactional state
   changes with audit events, and migrate existing onboarding rows to the new
   vocabulary.
6. **Workflow migration.** Add internship drafts/idempotency and map historical
   request/progress states without discarding prior decisions.
7. **Evaluation migration.** Add rounds, assignments, dates, and disclosure
   policy; backfill existing evaluations only after a policy is selected.
8. **Read models.** Add student/advisor home, directory, profile, and immutable
   history APIs with server-side scope, filtering, and pagination.
9. **Verification and rollout.** Run unit, PostgreSQL integration, IDOR/state
   abuse, type-check, lint, formatting, build, dependency audit, migration
   rehearsal, and the required disposable-Kali local self-pentest. Roll out
   gates behind reversible configuration if existing production data is
   incomplete.

Each database step must be backward-compatible with the currently deployed
server until the corresponding code is live. Destructive renames or enum value
removals require an expand/backfill/switch/contract sequence.

## Blockers and open decisions

The following must not be guessed during implementation:

- Eligible email domains and whether each registration type requires an
  institutional address.
- Evidence, approver, and service level for Student, Advisor/Staff, and
  Workplace Supervisor registration; whether any trusted registry can approve
  automatically.
- Student/personnel registry integration, fallback, and identity-correction
  authority.
- Workplace-supervisor invitation format, expiry, revocation, and single-use
  rules.
- Whether LINE email scope is used and how a missing/unverified contact email is
  verified.
- Account linking, unlinking, and recovery rules when one provider is lost.
- PDPA controller/processor roles, lawful basis, notice text/versioning,
  retention, correction, deletion, and optional-consent purposes.
- Definition and data source of an advisor's authorized academic scope and each
  advisor-directory category.
- Whether multiple active internship requests are allowed and whether terminal
  rejection is distinct from changes required.
- Daily versus weekly activity policy, reviewer, due dates, attendance
  aggregation, and revision-history retention.
- Evaluation round ownership, opening/closing behavior, late submissions, and
  which scores/comments each role may see.
- Official document templates, numbering, signatory/signature policy,
  NORMAL/CWIE differences, retention, regeneration, storage, and download
  authorization.
- Notification delivery channels and delivery/retry expectations.
- Production performance budgets, expected dataset sizes, backup/restore,
  encryption-at-rest controls, and monitoring requirements.

Until these decisions are approved, implementations should expose interfaces
and tests around the policy boundary without choosing business values.
